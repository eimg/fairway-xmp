# Desktop data browser

For task instructions, see [Browse and edit database records](https://eimg.github.io/fairway-xmp/#phpmyadmin), [Open a SQLite file](https://eimg.github.io/fairway-xmp/#sqlite) and [Import a MySQL SQL file](https://eimg.github.io/fairway-xmp/#import-sql).

**Data browser** is available in the macOS and Windows desktop panels alongside phpMyAdmin. Open it through **Browse Data** in the sidebar. The existing Linux terminal edition does not include the desktop data browser.

## Reading a row

Choose the eye action to open **View row**, a dedicated reader rather than a disabled edit form. The table name, row position and field count stay visible above a scrollable list. Column names/types and primary-key/generated/hex markers sit beside selectable values. Ordinary text wraps, line breaks are preserved, and SQL NULL is distinct from empty text. Large MySQL fields start with a labeled preview and explicit full-load or read-in-parts actions. Very large loaded text uses its own scrolling area to keep the dialog responsive. Values are tied to the displayed row snapshot; a later change prevents further chunk reads until refresh.

Use a field's copy button for its complete value, fetching any missing MySQL chunks first; NULL copies as the SQL token `NULL`, and empty text copies an empty string. **Copy row JSON** copies all fields with nulls/empty strings preserved and numeric values retained as exact strings. Binary values use the displayed hex representation. **Edit** switches to the row form only when the current source/table still supports safe keyed editing. Close or Escape returns to the table, including inside a maximized workspace.

## Indexes and foreign keys

Open a table's **Structure** tab to inspect its columns, **Indexes**, and **Foreign keys**. This metadata loads with the table, so switching from Rows does not start another request. Filtering remains in the SQL editor.

**Indexes** shows primary keys, ordinary indexes and unique indexes with their ordered columns. Existing descending/prefix/expression parts, non-default SQLite collations, partial indexes and advanced MySQL index types are shown without simplifying their definitions. SQLite index SQL is expandable; **Table SQL**, beside **+ Column**, opens the complete table definition in a modal with Copy. SQLite's INTEGER PRIMARY KEY is identified as a rowid key even though it has no separate physical index.

Choose **+ Index**, select 1–16 distinct columns in order, and optionally select **Require unique values**. The suggested name follows the table/columns until you enter your own name. Add/remove and Up/Down controls arrange composite index columns. Forms create ordinary ascending column indexes; use SQL for expression, prefix, partial, full-text, spatial and other advanced definitions. MySQL text/JSON and both engines' binary/generated columns use SQL for indexing. Unique indexes enforce the entire selected combination; multiple NULL values are permitted by both engines. Existing duplicate values produce an error without creating an index.

**Remove** requires typing the index name and a successful whole-database backup first. Table rows are kept; removing a unique index removes its uniqueness enforcement. The backend rechecks the displayed definition and rejects a stale/replaced index. SQLite also protects a composite unique index when a foreign key references its columns in a different order. SQLite performs the metadata recheck and removal under a write lock. Avoid concurrent schema changes from other tools, especially during MySQL administration. Primary keys, SQLite constraint-owned autoindexes, advanced indexes and indexes identified as supporting foreign keys stay read-only in this form. MySQL indexes supporting an automatic ID are also protected. Dependency checks are deliberately conservative: SQL remains available when another index could satisfy the same relationship. Normal row identity is recomputed after index changes.

**Foreign keys** is read-only. **References** lists relationships defined on the selected table; **Referenced by** lists relationships from other tables, including MySQL cross-database references. Each shows the constraint name (SQLite uses its engine-provided numeric ID as a display label), ordered child → parent column mappings, and ON UPDATE / ON DELETE rules. Omitted SQLite parent columns resolve to the parent's ordered primary key when available. SQLite enforcement is enabled for Fairway's connections; this does not configure the application's connections. The **Foreign keys** button in Create table and Structure opens a shared modal with engine-specific SQL examples and Copy. Create table shows a relationship declared in CREATE TABLE; Structure shows MySQL add/remove examples or a SQLite creation example with a brief rebuild note for existing columns. Closing the examples preserves the Create table draft. Foreign-key creation/editing and relationship navigation remain outside this form.

## SQLite project files

Choose **Open SQLite file…** in the top toolbar. This action is always visible and works with MySQL and all other services stopped. SQLite is a Data browser capability; it has no service card, port, password, or Start/Stop control. The page description explicitly names MySQL and SQLite.

Create the project file as usual (for example, Laravel's `database/database.sqlite`), then open it in Fairway. Existing unencrypted SQLite 3 databases and empty files are accepted. The picker includes an All files option for databases with other extensions. Fairway opens the original file in place; it does not import, move, or copy it. The selected filename and full path stay visible. Changes are saved directly to the file used by the project. Missing paths, folders, invalid files and encrypted files report an error; opening a missing path never creates a replacement database.

**MySQL** and **SQLite** are source tabs and stay available while the browser is idle. Choosing MySQL while the service is stopped shows Start MySQL and does not start it. Choosing SQLite before a file is chosen shows Open SQLite file and does not open the picker; the picker accepts `.sqlite` and `.db` (plus `.sqlite3`, `.db3`, and All files). While a file is open, its name, full path, and immediate-save warning sit with **Back up SQLite file** and **Close SQLite file** in one card under those tabs. Close releases the file. It does not delete the file, write to it, or open the picker. Up to six paths stay remembered locally. The SQLite tab returns to the latest one across app restarts. An explicit Close in the same session does not reopen it, including after a switch to MySQL and back. The empty state can reopen that last file, or open another file, only when that action is chosen. Returning through the sidebar keeps the current file, table, tab and query workspace. A moved/deleted file reports an error when reopened or refreshed; use Open SQLite file again to select its new location. Switching sources clears the SQL result/history and starts with an engine-specific example query. MySQL remembers its last selected database and table for this app session when switching back from SQLite; unavailable selections fall back to the current catalog.

SQLite supports table creation/rename/deletion; structure and table SQL inspection; row sorting/pagination, insertion, editing and deletion; adding ordinary columns; supported column deletion; index management and foreign-key inspection as described above. Creation forms offer `INTEGER`, `TEXT`, `REAL`, `NUMERIC`, and `BLOB`, with NULL/default and primary-key controls. Automatic IDs require a single `INTEGER` primary key. Column deletion needs SQLite 3.35 or newer and may be refused when constraints or dependent objects require rebuilding the table. Column renames/type changes, foreign-key changes and advanced definitions use SQL. Existing declared types remain visible without conversion to MySQL types. SQLite storage/affinity rules apply; it does not provide MySQL's fixed-precision DECIMAL semantics.

Form updates/deletes require a verified non-null primary or unique key. Nullable SQLite primary keys, partial/expression indexes and binary key columns are not treated as safe identities. Views and virtual tables are read-only in forms. Generated and binary values are read-only in row forms; BLOB storage is detected even in a TEXT column and displayed as hex. Row changes submit only edited fields and compare original values inside a write transaction, rejecting stale changes from another editor or the running project. A five-second lock wait reports busy/locked databases without silently retrying writes. Signed 64-bit integer values remain strings in the interface.

**Back up SQLite file** is on the open-file card. It saves a consistent `.sqlite` snapshot in Fairway's backups folder, including committed data in WAL mode. **Close SQLite file**, on that same card, releases the open file so later browsing does not update it. Confirmed table/column deletion and index removal must successfully back up the whole selected database first. Backups use SQLite's `VACUUM INTO`, rather than copying an active file or its sidecar files. Failed backups prevent schema deletion. Backups never overwrite an existing file; Open backups reveals the folder. Restore by opening the backup or, with the project and other database users stopped, replacing the project file through your normal file workflow. Row deletion requires confirmation but does not create an automatic backup.

The SQLite SQL editor supports selection/all execution, up to ten statements and 1 MiB of SQL per run, including quoted semicolons, comments and trigger bodies. Each result displays at most 200 rows. Queries are bounded by the shared 128 MiB worker/8 MiB response limits and a 30-second worker timeout. Cancel terminates that request's worker; completed statements remain committed. Finish transactions with COMMIT or ROLLBACK in the same run; unfinished transactions roll back and report an error. SQL is an administrative tool and does not automatically back up changes. SQLite files and backups are separate from the MySQL-only `fairway db` CLI and environment/update MySQL backups. phpMyAdmin is shown only for MySQL.

## MySQL

Start MySQL from the browser's empty state or Environment. phpMyAdmin also needs Nginx running.

- Create/delete databases; rename an **empty** database, preserving its character set and collation. MySQL has no atomic database rename. Populated schemas are refused without changing their contents; use export/import into a new database and update project connection settings. Close other applications that might create objects during a rename.
- Create/rename/delete tables. The column form covers common integer, decimal, floating-point, character/text, Boolean, date/time, JSON, and BLOB types; length/precision/scale, unsigned, NULL, literal/NULL/current-timestamp defaults, primary keys, and integer auto-increment. A new MySQL column starts required; a new SQLite column starts nullable. Composite primary keys can be selected when creating a table. Index management and foreign-key inspection are available in Structure; engine and foreign-key editing forms are deferred.
- Add/edit/delete ordinary columns and inspect the table's SQL. Existing primary keys, comments and text collations are preserved on supported column edits. Generated, fractional time, expression-default and other advanced definitions stay in SQL/phpMyAdmin rather than being simplified by a form.
- Browse rows, sort by a column, and page up to 50 rows at a time (wide tables use smaller pages to keep responses bounded). The row grid uses the height left in the window when the rows need it, and a short table stays only as tall as its rows. Cells stay clipped; open a row to read a long value. Use the SQL editor for filtering. Insert using explicit values or SQL NULL; only auto-increment columns and columns with non-NULL defaults offer a default option. Nullable columns without a non-NULL default start blank and save NULL, and the field accepts typing immediately. Choose Value while that field is blank to store an empty string; clearing a nullable field returns it to NULL. Required columns start in value mode. Every row opens in a read-only view with distinct empty-text and SQL NULL markers. Large fields initially show a labeled preview; load the complete value or read it in bounded parts. Edit/delete requires a primary key or non-null unique key. Views are read-only; keyless tables allow browse/insert. Binary, BIT, and spatial values display as hex and are read-only in row forms.
- Drag the divider to widen the table list or data panel. The divider also supports Left/Right arrow keys (Shift for larger steps), Home/End, and double-click to reset. Hide/show tables is an icon in front of the table name; restoring the list retains its chosen width while the page stays open. Fold the main sidebar to icons when the table still needs that width. Resizing the window keeps room for the data panel. Dropdowns use consistent control heights across desktop WebViews and browser previews.
- Insert row sits beside the table actions menu. Database and table export/rename/delete are grouped in their respective actions menus. Table metadata loads with the table, so switching Rows/Structure does not start another operation or dim the screen. Empty row lists have an inset message and the SQL heading stays on one line for ordinary names.
- Database/table changes keep the current workspace visible until the complete replacement is ready, then update the catalog, selection, rows, and structure together. If a table/view fails to load, the new catalog and selection are still published with empty data and an inline retry error, so other tables and SQL repair remain available. Browsing temporarily blocks interaction without fading controls; one small loading indicator appears after 200 ms without shifting content. Database requests retain the native operation guard but do not show a second app-wide busy indicator. Sidebar navigation preserves the selected database/table, tab, SQL text/results/history, and table-list sizing, refreshing the catalog when returning. Leaving cancels an active request; returning waits for cancellation before starting a refresh.
- Success and error messages stay in a fixed notice. A long message scrolls inside that notice, and the page position and keyboard focus stay where they were. SQL editor with selection/all execution, Command/Ctrl+Enter, multiple result sets, readable row-change summaries, timing, cancellation, errors, and ten recent successful queries kept only while the page is mounted. SQL changes take effect immediately; Cancel cannot undo completed statements. The SQL heading’s question-mark tooltip holds execution/result-limit/import guidance. Each result grid scrolls internally and is capped at the smaller of 360 pixels or 45% of the window height.
- Export a whole MySQL database from Database actions, or the selected table from its heading, to the app's backups directory. **Open backups** is always available at the bottom right, including maximized view and SQLite. CLI examples remain in this documentation rather than the browser footer. Open SQLite file stays in the page heading.
- Query results say **1 row inserted**, **2 rows updated**, **0 rows deleted**, or **1 row returned**. DDL and session commands show **Statement completed**. A single result uses that summary as its heading; multiple results keep numbered headings. Upserts, REPLACE and ambiguous stored-program/multiple-result scripts retain generic affected-row counts rather than claiming an inaccurate insert count.

MySQL converts character values to UTF-8 inside the database, including latin1 columns. Numeric values are returned as database-generated strings so PHP does not round DOUBLE values through its default floating-point precision. FLOAT values are widened exactly to DOUBLE before text conversion so numeric keys round-trip and fingerprints distinguish nearby stored values. BIT values use whole-byte hex with leading zeroes. Identifier limits count Unicode characters rather than UTF-8 bytes.

MySQL row pages include indexed key values plus a SHA-256 fingerprint over all complete row values and column/key metadata. Update/delete forms lock through an ordinary primary/unique-key predicate, recheck metadata and the fingerprint, and include the fingerprint in the write. They reject concurrent changes anywhere in the row, including beyond a displayed preview, binary values, NULL changes and case-only text changes. No-op saves still validate the row. Views and tables without a visible, complete, non-null, nonbinary unique key stay read-only for updates/deletes. Read-only large values in those tables can still be retrieved by their complete fingerprint. Fingerprinting reads full values on the server; it does not make large tables or keyless reads free of server work, and the existing timeouts still apply.

Large MySQL fields use SQL-side previews of at most 1,024 characters per field and an adaptive page budget. **Load full** and **Copy** retrieve complete values in chunks of 131,072 database characters, verifying the row fingerprint on each request. Full-value form loads and copies are limited to 16 MiB of UTF-8; **Read in parts** remains available for larger values, with an explicitly labeled **Copy shown part** action. Copy row JSON resolves complete values and refuses oversized results instead of copying previews or partial JSON. Closing a dialog cancels an active cell read. Clipboard permission errors remain in the reader; a loaded value can still be selected manually.

A truncated field starts in **Keep current value** mode in the edit form. **Load … to edit** retrieves its complete original, while **Replace value** starts a deliberate replacement. Saving another field never submits or overwrites the preview. Forms send changed fields and the compact row reference. Larger changed text travels through private native-created temporary files to the PHP worker, with a 16 MiB aggregate text limit; renderer-supplied file paths are refused. Normal completion, failure and cancellation remove those files. The worker's existing 2 MiB JSON request and 8 MiB response caps remain in place. SQLite retains its existing row protocol and limits.

## Import MySQL SQL files

Choose the target MySQL database, then **Database actions → Import SQL file…**. Pick an uncompressed SQL dump and type the target database name to confirm. Create the target database first if needed. The native backend streams the file through the bundled MySQL client, supporting full dumps and stored-program `DELIMITER` directives without the query editor's 1 MiB/30-second limits. It never loads the whole dump into the browser. A full backup of the selected database must succeed before import begins, and the result/error includes its path. The dialog distinguishes creating a backup, importing SQL, cancellation and recovery refresh. **Cancel import** stops the client; backup generation finishes before cancellation is checked and the dialog explains this wait. Completed statements are not undone. Errors can leave partial changes, and the browser refreshes its catalog afterward. Canceling or failing an import clears the typed confirmation before another attempt.

SQL dumps can explicitly switch or qualify databases; only the selected target is backed up automatically. Review dumps and avoid concurrent database writers. Client shell commands and LOCAL INFILE remain disabled, using the same implementation as `fairway db import`. SQLite stays backup-only; open the original database file rather than importing SQL into it.

Both database adapters run bundled PHP/PDO over private stdin/stdout; they add no HTTP database endpoint or new runtime dependency. MySQL credentials stay in the native backend. Form values use bound parameters and identifiers are validated/quoted. Numbers remain strings, including MySQL BIGINT/DECIMAL values that JavaScript cannot represent exactly. Row changes compare all original values, including case-sensitive text, to reject stale edits. A live primary/unique key is verified again before writing.

Database/table/column deletion, index removal and supported column changes require confirmation and first create a full SQL export of the selected database. A failed backup prevents the change. Row deletions use a confirmation dialog and do not export the database. Arbitrary SQL is explicitly an administrative tool and does not receive automatic backups. Completed statements in a failing SQL script may already have changed data; refresh before retrying. System databases are hidden/protected by forms; the SQL editor has administrator access.

The display caps query results at 200 rows and ten result sets. MySQL executes all submitted statements, drains later results to detect errors and transaction completion, and explicitly reports when only the first ten result sets are shown. Ten is a display limit, not an execution guard. Finish COMMIT or ROLLBACK within the same run; unfinished transactions roll back with an error instead of reporting success. SELECT without an explicit LIMIT has a 201-row session cap. Queries use unbuffered results, a 128 MiB worker limit, an 8 MiB response limit, 15-second SELECT limit, five-second lock waits and a 30-second worker timeout. Cancel kills the current owned connection's query and closes its worker. Exports and protective backups finish before cancellation can be checked; full-file imports (UI or CLI) and exports are not given the interactive query timeout.

Query UPDATE summaries count changed rows on MySQL, so assigning an existing value reports zero rows updated. Form saves still count matched rows to preserve no-op save/conflict behavior. SQLite counts matching rows even if values were unchanged, so its UPDATE summary explicitly says rows matched for update.

## Desktop command line

Choose **Enable command-line tools** in Settings and open a new terminal. On macOS and Windows, the compact section lists PHP, Composer, and `fairway db`. Its question-mark help contains terminal checks, MySQL requirements, and upgrade guidance; command paths/detection are under Command details. Existing installations may need **Remove from user PATH** then **Enable command-line tools** once to create the new `fairway` launcher (`fairway.cmd` on Windows). Direct invocation also works:

```sh
"/Applications/Fairway XMP.app/Contents/MacOS/fairway" db --help
```

On Windows use Command Prompt or PowerShell; quote paths containing spaces. For SQL arguments, use double quotes in Command Prompt instead of the single quotes shown in the shell examples below.

```sh
fairway db list
fairway db tables school
fairway db create school
fairway db rename empty_school new_school --yes
fairway db drop school --yes
fairway db query school 'SELECT COUNT(*) FROM students'
fairway db export school --output ~/Desktop/school.sql
fairway db export school --table students --mode structure --output ~/Desktop/students-structure.sql
fairway db export school --mode data --output ~/Desktop/school-data.sql
fairway db import school ~/Desktop/school.sql --yes
```

MySQL must be running. Results are JSON. Export modes are `all`, `structure`, and `data`; without `--output`, exports go to the app's backups directory. An export is published only after success and never overwrites an existing file. Create the target database before importing. Single-database exports omit `CREATE DATABASE` so ordinary tables can be imported into another selected database. Views/routines/triggers may contain explicit original-schema references; review those when migrating names. Incoming SQL may explicitly switch databases. Import stops on SQL errors and may leave partial changes, with a pre-import backup available. Local client shell commands and LOCAL INFILE are disabled during import. Avoid other database writers or stopping MySQL during administration.

## Verification and review

Run `npm run test:unit` for the fast log-view, SQL-result and bounded full-value helper regressions. The native browser bridge also supports real database cancellation and observes external-terminal working directories without opening host terminal windows.

`npm run dev:ui` provides the same interface with clearly labeled in-memory fixtures. Select Running, then Data browser. Fixtures cover ordinary/keyless tables, views, exact large numbers, NULL/empty text, CRUD/schema forms and query pending/error/cancel states. Fixture SQL intentionally supports only a few SELECT examples; it is not a SQL engine.

`npm run test:ui` runs Chromium and WebKit at normal/minimum window sizes and attaches screenshots to the HTML report. The native example exercises isolated bundled MySQL, actual schema/row SQL, keys, concurrency conflicts, Unicode, exact values, cancellation, SQL export/import and recovery guards:

```sh
cargo run --manifest-path src-tauri/Cargo.toml --example data_browser_smoke \
  --no-default-features --locked -- "$PWD/.runtime-work/data-browser-smoke"
```

Use a fresh scratch directory for each run. It starts its own MySQL on free ports and shuts it down afterward. Both desktop installer workflows also run this example. Browser fixtures do not establish native correctness, and neither replaces a human check in the native WebViews before release.

SQLite verification uses real project files and requires no services:

```sh
python3 -m unittest discover -s tests -p test_sqlite_browser.py -v
cargo run --manifest-path src-tauri/Cargo.toml --example sqlite_browser_smoke \
  --no-default-features --locked -- "$PWD/.runtime-work/sqlite-browser-smoke"
```

The Python tests use the staged runtime (or `FAIRWAY_TEST_RUNTIME`) and cover exact values, external writes, locks, keys, BLOBs, views, transaction/trigger scripts, result caps and SQLite loading across staged PHP versions. The native smoke adds missing/invalid file preservation, backup restoration, failure-before-delete guards and cancellation. `sqlite-browser.spec.ts` covers visible discovery, engine-specific forms, navigation and remembered files in Chromium/WebKit; `sqlite-browser-native.spec.ts` exercises the production UI through the Rust/PHP bridge against the original Unicode project path with MySQL stopped. The native test bridge substitutes the OS file picker with an isolated fixture path; a human must still check the actual macOS/Windows picker and native WebViews.

Index/relationship regression tests add composite unique enforcement, duplicate-creation failure, stale-index refusal, primary/constraint/dependency guards, implicit/composite foreign keys and incoming relationships. `schema-details.spec.ts` exercises ordered index forms and inspection in Chromium/WebKit at normal/minimum sizes. `schema-details-native.spec.ts` creates real indexes through the production UI against both bundled engines, checks duplicate errors and reference rules, removes an index with a protective backup and verifies inspection remains read-only. Both desktop candidate workflows include this native test.

Pass 8 adds `row_edit_smoke` (a fresh disposable directory is required):

```sh
cargo run --manifest-path src-tauri/Cargo.toml --example row_edit_smoke \
  --no-default-features --features terminal --locked -- /tmp/fairway-row-edit-check
```

This example checks latin1/BIT/FLOAT/DOUBLE representations, character-counted identifiers, complete large-value reads, multi-megabyte changed values and temporary-file cleanup, stale tail/binary/NULL/schema changes, cancellation cleanup, composite keys, views/keyless reads, no-op saves and competing row locks. It repeats numeric/no-op/chunk checks across all bundled PHP versions. `row-values.spec.ts` checks preview safety, full copies, paging, failure/cancellation and edit preservation through the production React components. The expanded `data-browser-native.spec.ts` also crosses the production UI → Rust → PHP → MySQL path for multi-megabyte edits and stale-write rejection. Platform-native WebView/clipboard and Windows staging acceptance remain separate from browser-engine tests on macOS.

Both desktop candidate workflows run this real-database example and browser input through the native stdio test bridge. The latter starts isolated bundled MySQL and checks database/table creation, Unicode row insertion/editing, and exact SQL results. The bridge is test-only and opens no HTTP database endpoint. Optional [platform checks](testing.md#optional-platform-checks) cover native WebViews, dialogs and installer behavior.

## Windows filesystem paths

PHP startup configuration also uses compatible path aliases when available, so the database driver loads from user profiles containing Unicode characters. Project names and query/row text keep their original Unicode values.

MySQL Server on Windows restricts file paths to the current ANSI code page ([upstream restriction](https://dev.mysql.com/doc/refman/9.7/en/windows-restrictions.html)). Fairway uses existing NTFS short-name aliases for MySQL configuration, data and log paths when available, without moving or renaming student data. PHP, the terminal folder picker and project paths retain their Unicode paths. When aliases are unavailable and the paths cannot be represented in the active code page, MySQL startup reports the limitation and keeps existing data intact. A filesystem with short-name aliases or paths compatible with the Windows locale is required in that case.

## Windows backup/export identifiers

On Windows systems whose process code page is not UTF-8, the bundled MySQL command-line clients cannot reliably receive non-ASCII database/table names. Fairway reports this explicitly instead of attempting a potentially misdirected export. Whole-environment backups require ASCII database names; table exports require ASCII database and table names. Imports require a successful target-database backup first. Unicode row values and normal in-app queries remain supported.

An automatic update that cannot complete its database backup stops before installation and keeps existing services/data intact. Use ASCII schema identifiers for coursework that needs these backup/export operations. UTF-8 Windows system locales are exempt from this argument limitation, but no system locale setting is changed by Fairway. The owner accepted this disclosed RC limitation on 2026-10-19; broader Unicode CLI backup support remains a follow-up.

The bundled phpMyAdmin can make a manual SQL export for Unicode identifiers. That manual export does not override the automatic updater's backup requirement.
