# Fairway XMP development environment

## Product

Display name: **Fairway XMP** on Windows, macOS and Linux. The green application mark is shared by the app, Windows installer, and uninstaller. The macOS bundle is `/Applications/Fairway XMP.app`; installer hooks and removal target only that bundle.

A classroom PHP development environment with a desktop control panel on Windows/macOS and a terminal dashboard on Linux.
Supported targets: Windows 10 22H2 / Windows 11 x64, macOS 15+ Apple Silicon, and Linux x86_64 with glibc 2.35+. Linux ships as a terminal edition; CI covers its installer and five distro runtimes, with release-owner testing still encouraged.
No Docker/WSL requirement, distro-specific Linux packages, ARM Linux or musl support, Intel Mac packages, Node/npm bundle, or Laravel-specific project management.

## Application and runtimes

Tauri 2, Rust service manager, React/TypeScript UI. Exact versions and required PHP extensions are recorded in `runtime-manifest.json`. Download inputs are pinned by SHA256 in `runtime-downloads.lock.json` once prepared and reviewed. Runtime preparation never installs Homebrew or system services.

The alpha 2 runtime uses PHP 8.5.11 CLI/FastCGI, stable Nginx 1.30.5, MySQL 9.7.2 LTS, phpMyAdmin 5.2.3, Composer 2.10.3, Mailpit 1.31.6, CA trust roots, native runtime libraries and upstream notices. Mac Nginx is compiled from its pinned upstream source using pinned PCRE2/OpenSSL bottles and the macOS SDK's zlib. No system installation or Homebrew service is required. Windows inputs are official x64 ZIP distributions with checked SHA256 pins.

New builds after PR #1 bundle PHP 8.0–8.5, with PHP 8.5 selected by default. One persisted `php-version` selection controls websites, CLI PHP, and Composer. Desktop selection is a dropdown inside collapsed Advanced settings, saved with the ports; Linux exposes `fairway php-version`. Switching requires stopped services, validates the selected runtime, and regenerates configurations and installed CLI launchers. Failed settings changes restore the previous configuration. Windows loads the ZIP extension DLL only when present; Linux recovery verifies the selected PHP-FPM executable. Beta 1 publishes that selection in installers that report `0.1.0-beta.1`. Remaining source-provenance work is tracked in `docs/release-follow-ups.md`.

Linux uses a separate `cli` Cargo feature, without Tauri, WebView or GUI dependencies. Runtime inputs are SHA256-pinned in `runtime-linux-downloads.lock.json`; PHP and Nginx are compiled on the glibc 2.35 baseline. MySQL uses the official generic x86_64 archive. Each component bundles its native library closure with relative RUNPATHs; MySQL and PHP OpenSSL versions remain isolated. Build validation rejects newer glibc symbol requirements. Corresponding source archives include the exact app commit, PHP/Nginx/MySQL sources and Ubuntu sources/patches for copied libraries.

## Linux terminal edition

`fairway` opens the ANSI terminal dashboard; CLI commands provide status (including JSON), Start/Stop/Restart all or Nginx/MySQL/Mail, logs, ports, backup, bundled PHP/Composer/MySQL tools, a shell and managed PATH integration. PHP-FPM follows Nginx; PHP CLI does not require starting web services. phpMyAdmin uses the displayed browser URL.

A detached user supervisor owns the service manager. A private Unix socket and lifetime advisory lock coordinate multiple clients; mutations run sequentially, while status/log requests report busy promptly during an operation. Requests identify the installation before performing actions. The services and supervisor do not run as root; local `.test` address setup uses a short-lived privileged helper after the user approves it. No systemd dependency or automatic service startup. `q`/Ctrl+C close the TUI while services persist; `Q`/`fairway shutdown` queue graceful shutdown after pending operations, then stop services and the supervisor. TUI commands are delivered before acknowledging their keys, so closing immediately cannot cancel an accepted action. Failed shutdown leaves the controller available. Linux process recovery verifies `/proc` executable and exact service configuration before adopting MySQL/Nginx/PHP-FPM; recovered ownership also checks process start time to reject a reused PID.

The offline `.run` and equivalent `.tar.gz` install under `~/.local/share/fairway-xmp` (custom dedicated prefix optional), with versioned release directories and a current symlink. Reinstallation backs up initialized student databases and gracefully shuts down before switching runtimes. Bash/Zsh integration exposes Fairway/PHP/Composer; other shells can invoke the absolute path. Uninstall always preserves coursework, databases and backups. Manual updates only; no desktop updater on Linux.

Modal text fields and dropdowns use an inset keyboard focus ring. Sites and database forms share a padded scrolling body with fixed headings and action footers; focused controls, scrollbars, and buttons stay inside the modal at the 820×650 minimum size. Small controls and buttons retain a visible outer focus ring with space around it.

Page headings and sidebar navigation omit decorative eyebrow captions. The desktop sidebar groups Environment, Terminal and Logs at the top, Manage Sites / View Mail / Browse Data under a subtle divider, and Settings / Updates in a group anchored above Getting started and a centered version at the bottom. Group names are available to assistive technology without visible captions; the local-learning badge and repeated product name are omitted. The XMP brand label uses normal letter spacing.

Shared operation results appear in a fixed, dismissible notification without scrolling the page or moving focus. Successes use polite status announcements and errors use assertive alerts; long messages scroll within a bounded notification and remain until dismissed, replaced by another operation, or cleared by navigation. Page-specific results that arrive after navigation are suppressed. Identical backend error events are deduplicated until a different error or a new explicit operation. CLI enable/disable messages retain the new-terminal/restart-editor instruction. Form validation stays in its existing form, and Logs auto-follow and terminal focus remain independent.

Environment places Nginx, PHP, MySQL and phpMyAdmin in a 2×2 grid, with Mail in a compact full-width row below. Mail groups its identity and status on the left, inbox address in the middle, and service/log controls on the right; unavailable/error details use their own row. Narrow layouts stack these groups without removing controls. A separate Workspace details section pairs Document root and Database connection in equal-width reference cards with matching headings and action footers. Document-root paths wrap in full. The redundant Environment terminal shortcut is removed; Terminal remains available in the sidebar and through Ctrl+backtick.

Data browser navigation preserves its workspace state across sidebar visits. Database/table loading replaces catalog metadata and rows together, keeps the previous view visible and inert until ready, and uses one delayed local indicator without dimming controls or shifting layout. The native operation guard remains active. Returning during cancellation waits for the prior request before refreshing.

## Services

Default loopback ports: website 8800, phpMyAdmin 8801, MySQL 13306, internal PHP FastCGI 19000, mail inbox 8802, mail SMTP 11025. Settings saved before the mail catcher keep all existing ports. On first load, missing mail ports use the defaults or the next distinct unprivileged port when a default is already configured for another service; the chosen ports are saved atomically. Explicitly saved mail ports are never reassigned, and invalid settings are preserved and reported.

Mail runs Mailpit's official release binary as an optional fifth service, bound to 127.0.0.1 with its database under application data. Start all includes it when the runtime has it; a runtime without it keeps every other service usable. PHP's `mail()` uses it through `sendmail_path` (`mailpit sendmail`) on macOS/Linux and `SMTP`/`smtp_port` on Windows, so mail never leaves the computer. Mailpit writes no PID file, so Fairway records `mail.pid` and, on macOS/Linux, adopts a leftover Mailpit only when its executable and exact command line match. The desktop Mail page is a native inbox: the backend reads Mailpit's REST API over loopback (list/search, open, delete, delete all, and saving an attachment through a native save dialog) and the page polls while open. HTML email renders in a fully sandboxed `srcdoc` frame under the app CSP, so scripts and remote images stay blocked. It also offers the SMTP address and Laravel `.env` settings; The Mail card on Environment opens this page, which uses the full window width; Mailpit's own web UI remains available through Open in browser.
Nginx owns two listeners and serves phpMyAdmin; phpMyAdmin is not an independent server process.

Sites are explicit registrations saved in `sites.json` in the data directory: a display name, a DNS-label domain served as `<domain>.test`, an absolute web root anywhere on disk, an HTTPS flag, and an optional "route missing paths to index.php" fallback. Nothing is discovered from folders and there is no framework detection. An existing `projects.json` is read once, written as `sites.json`, and removed. Registering, editing, or removing a site validates the list, writes the Nginx configuration, and runs `nginx -t` and reload; on failure the previous list and configuration are restored, so the basic localhost server keeps working. A missing web root is shown as unavailable; its server stays configured and answers 404, so restoring the folder restores service without another edit. After a change, Fairway syncs only its marked hosts-file block to the registered domains with OS administrator approval; a declined or failed sync leaves the site saved and the UI offers a retry. Startup and service controls never touch the hosts file or certificate trust. Removing a site keeps its files. Uninstall removes the managed entries. Port 80 and portless site addresses are not part of this release.

Desktop Sites uses responsive entries with full URLs, web root paths, readiness states, Copy URL, and a compact actions menu with left-aligned single-line labels, icons, and a divider before Remove site for opening the web root, opening a site terminal, editing, and removing. A page-level web-server control starts Nginx/PHP without starting MySQL; unavailable/runtime/address/HTTPS/server states explain why Open is disabled. Save messages use the returned readiness and HTTP/HTTPS URL. An unreadable saved list surfaces an error with retry and the saved-list path, disables registration changes, and is never shown as an empty list; CLI status and the TUI also report the error. The add/edit form uses an explicit App type choice for direct file serving or a front controller, readable helper text, and a conditional warning when the chosen root is inside the shared document root. All sites use the displayed shared PHP version.

Each site can enable HTTPS on loopback port 8443 without changing HTTP on port 8800; Linux exposes `fairway site https DOMAIN on|off`. Fairway creates one local `.test`-constrained certificate authority and signs a leaf certificate containing the exact HTTPS domains. The first enable installs per-user trust (macOS login keychain, Windows user Root store, Linux system store via sudo/pkexec) after an explanation; private keys stay in the user's application data. Removing the last HTTPS site also removes the trust; after turning HTTPS off, the user can remove it explicitly; uninstall also removes it and clears saved HTTPS flags. Laravel applications can set `APP_URL` to the secure URL for generated links.

Start all preflights all ports before launching. Ports are validated, distinct, unprivileged, and saved only while services are stopped. Conflicts suggest an available alternative and show the occupying application where available. No silent port reassignment.

The application tracks processes it starts. Nginx startup starts PHP; stopping or restarting Nginx through the panel or tray also stops or restarts its PHP worker. PHP has status and logs in the panel but no independent service controls in the panel or tray. PHP CLI remains available without running web services. Internally, stopping PHP first stops Nginx. Starting/stopping MySQL is independent. A partial Start all failure rolls back newly started services while retaining previously running ones. MySQL is shut down through authenticated mysqladmin and is never forcibly killed. A surviving MySQL instance can be recovered only when its PID and exact runtime/config command identity match this installation. On macOS and Linux, startup also recovers surviving Nginx and the selected PHP-FPM master only when both their executable path and exact service/configuration title match. A crash or force quit therefore leaves services controllable after reopening; unrelated processes and other Fairway data directories are not adopted.

Minimizing and closing the window leave the application and services running. A native macOS menu bar / Windows system tray menu offers Show Fairway XMP, Start all, Stop all, individual Nginx/MySQL/Mail Start/Stop, Open phpMyAdmin, and Quit. On macOS, small colored dots follow the text using AppKit attributed titles with a separate font size. Windows uses small colored bitmap dots in the native icon column, avoiding monochrome emoji rendering. Native menu layout keeps the labels aligned. Nginx/MySQL/Mail show green when ready and red when stopped or not ready. Start all and Stop all use plain text without dots. Their enabled state reflects the owned processes (PHP, Nginx, MySQL, and Mail when available); phpMyAdmin is not counted as another process. Stop all remains enabled when only Mail runs, and Start all remains enabled when Mail is available but stopped. Runtimes without Mail can reach the fully started state, while a running Mail process is always counted even if its binary was removed. The status snapshot reports actual Mailpit executable availability as `mailAvailable`. The macOS tray Quit item displays the native Cmd+Q shortcut. phpMyAdmin shares Nginx and has no independent Start/Stop. Reopening the app restores the existing window; macOS Dock reopening does the same.

Tray and panel actions share one Rust operation guard and service manager. Native status monitoring continues while the window is hidden. Quit (including macOS Cmd+Q/application Quit) prevents new operations, waits for an existing operation, and gracefully stops all services before allowing exit. Repeated quit requests cannot bypass shutdown. If shutdown fails, the window reopens with the reason and Quit can be retried. Tray creation must succeed before the app can run with close-to-background behavior. Services do not start at login or automatically at app launch.

Status distinguishes an owned live process from a ready endpoint. Website/phpMyAdmin listeners are checked against a Fairway XMP health endpoint. Unexpected process exits surface a log hint.

## Database

Fresh initialization creates a random private root password and a local teaching account `fairway` / `fairway`, with a `fairway` database. The teaching account may create/manage student databases locally. phpMyAdmin uses cookie authentication and disallows root login.

Student connection host is explicitly `127.0.0.1` with the saved database port. Port changes update phpMyAdmin and copyable connection settings; project files are never silently edited.

Logical backups include student databases, routines, events, and triggers and exclude MySQL system schemas. Failed exports are not presented as completed backups. Existing database data and credentials are never silently reset on an error.

Logical exports reserve a unique timestamp/random filename with exclusive creation, publish only after a successful dump, and clean partial files on setup/dump/publish errors. The native smoke check imports the dump into a separate fresh MySQL instance and verifies data across databases, views, foreign keys, triggers, routines, disabled events, and PHP access. User recovery through the bundled client is described in `docs/backup-and-restore.md`.

Before the first supported MySQL 8.4 → 9.7 startup, preserve the stopped physical database, credentials, settings and version markers under the user's backups folder. Record the completed backup before starting MySQL; failed startup retries never replace it. Record the new database family after authenticated provisioning succeeds. Reject unknown transitions and attempted downgrades. Fresh initialization records its engine version separately from account provisioning so interrupted setup can retry. Test migration against isolated alpha 1 data before release; Mac and Windows isolated migration checks have passed. Both platform installers have also been installed and tested by the release owner.

## First-party data browser

The macOS and Windows desktop implementation keeps phpMyAdmin alongside a first-party data browser. It provides database/table creation and deletion, empty-database rename, table rename, common column definitions and supported column edits, row browse/sort/pagination and CRUD (filtering through SQL), and a cancellable SQL editor with bounded results. The table sidebar has a draggable, keyboard-accessible divider and a hide/show control that retains its width; dropdown heights are normalized across desktop WebViews. Database/table export, rename and delete live in actions menus. Insert row shares the table toolbar with its menu and the styled sidebar toggle. Row insertion offers automatic/default values only for auto-increment columns or non-NULL defaults; other fields start with an explicit value or NULL when allowed. SQL guidance is in a help tooltip and result grids scroll internally with a 360px/45vh height cap. Rows/Structure share preloaded metadata to avoid operation-state flashes during tab changes. Populated-database rename is explicitly deferred to export/import; primary/unique row identity and optimistic conflict checks prevent ambiguous form edits. Views and binary values are read-only in row forms. Destructive schema changes and supported column edits save a SQL backup first. Desktop command-line integration adds `fairway db` administrative commands, including full SQL export/import. Linux receives no new command surface. Architecture, limits, verification, and usage are documented in `docs/data-browser.md`. This feature ships in beta 2.

The snapshot reports the app-owned launcher paths separately from inherited PATH resolution. The UI labels configuration as Added to PATH, shows the installed commands, and explains checking them in a new terminal. Inherited command resolution is in expandable detection details; missing commands there do not imply the installed launchers are missing. Open terminal places the bundled launchers first for that session.

## Embedded desktop terminal

The Terminal sidebar page opens a local interactive PTY in the default web directory (`fairway/www`). The selector labels it Default folder; Terminal copy describes general projects rather than coursework. Ctrl+backtick opens or focuses the selected terminal. Up to two tabs can run independently, so a development server can keep running while another shell runs Composer or migrations. Each tab retains its output across navigation; restarting, ending, or closing a tab affects only that shell. Closing a running tab requires confirmation. Keyboard-accessible tabs support arrow keys and Home/End. The expanded view keeps both tabs accessible.

A Start in picker lists project folders directly inside the default directory and registered site web roots, refreshing when opened or focused. Sites whose selected folder is named public also offer an explicit application-folder choice (its parent). The Sites actions menu can open either location, focusing an existing tab at that location or creating one in a free slot. When both slots are occupied, it asks the user to close a tab and leaves both sessions intact. It applies only to a new tab; existing commands never receive an injected directory change. Native validation rejects missing/non-directory choices, path traversal, and default-directory symlinks outside that root. Registered site selections use domain tokens resolved against the saved list, permitting those explicit locations outside the default directory without accepting arbitrary absolute paths over IPC. Stale or removed registrations fail before replacing any session. Folder names may include spaces and Unicode and do not require domain setup or framework detection. A restart uses that tab's original starting folder.

React lazily loads xterm.js and keeps both sessions mounted while navigating; Rust owns the shells independently of managed services. macOS uses an app-owned zsh configuration without reading personal startup profiles; Windows uses Command Prompt with AutoRun disabled. Session-only PHP/Composer launchers work without persistent PATH integration. Fairway's launchers remain first, followed by its Composer global commands, inherited PATH, and common Unix user/system locations, including Apple Silicon Homebrew and ~/.local/bin. No tool installation or personal profile changes are performed. Regenerating settings refreshes these launchers for the selected PHP version; already-running commands keep their current interpreter.

On macOS, Remember commands in new sessions is enabled by default and can be disabled for subsequent new/restarted shells without interrupting existing ones. Zsh retains about 1,000 commands in a private app-owned history file shared between tabs; a leading space omits a command. Password-prompt input and terminal output are not recorded. Private sessions retain in-memory recall without writing command history. Windows retains Command Prompt's in-session history and does not persist it across app restarts. History never changes the user's normal shell history files.

The terminal supports interactive input, Ctrl+C, copy/paste, clear, resize, confirmed restart/end, exit status and startup recovery. Find searches the buffer and scrollback with Enter/Shift+Enter for next/previous and Escape to close; Ctrl/Cmd+F opens it. Text size is adjustable from 10–24 pixels with Ctrl/Cmd+plus/minus and reset with Ctrl/Cmd+0; this preference is saved locally. An expanded view provides more space. Display and PTY dimensions are bounded together; resize failures keep commands alive and offer retry. Existing terminals remain accessible during unrelated service/database operations; creation respects the native operation guard. Navigation and hiding/closing the window retain both sessions. Explicit Quit and update installation close all shells; a new app launch starts fresh. A renderer reload replaces its prior workspace and closes stale shells. Each session has an ID, so delayed requests cannot affect a replacement or another tab.

There are no splits, remote shells, or saved terminal transcripts. Commands run as the current user with normal filesystem access. Terminal output is never inserted as HTML or automatically opened as a link. Each native output buffer is capped at 256 KiB with backpressure, drained in 32 KiB batches after renderer acknowledgement; visible scrollback is capped at 3,000 lines per tab. Windows jobs track each command tree; Unix cleanup hangs up the attached foreground group and shell, escalating if needed. Browser previews cannot open shells; UI-test mode uses labeled, non-executing fixtures. Routine Windows/macOS CI runs terminal unit tests; installer workflows additionally exercise browser input through real PTYs and packaged PHP/Composer, real database CRUD through PHP/PDO, and database export/import/cancellation against bundled MySQL. These features ship in beta 2.

## Installation and removal

Windows NSIS current-user installer checks OS build, handles Visual C++ and WebView2 prerequisites, enables CLI integration, and exposes uninstall cleanup choices. macOS pkg installs the app and enables integration only for the logged-in account; a resource-bundled uninstall utility removes integration and moves the app to Trash.

Uninstall requires stopped services and preserves coursework/data by default. Deleting data and deleting coursework are separate explicit choices. Shared prerequisites are not removed. Installation/update/removal must not terminate unrelated PHP, Nginx, or MySQL processes.

The macOS uninstaller's `--yes-keep-data` mode runs profile cleanup as the student, tries to move the app to their Trash, and uses administrator access only if that move fails. Installer lifecycle CI exercises this against a root-owned package installation.

## Troubleshooting logs

The desktop has one global Logs page in the core group below Terminal. Service log buttons open this viewer with the corresponding source selected; there are no separate log dialogs. Problems only defaults on; source filters, Search, Live/Pause, paused Refresh and Copy shown support troubleshooting. Warnings, failed requests and unclassified output remain visible by default. The Site filter uses recorded request host metadata: an address scope shows its requests plus PHP output explicitly labeled Shared PHP / All sites. Other service logs and older requests without a recorded host stay in All sites. Registered and recently observed hosts are offered, and service shortcuts clear site scope. No new per-site logging configuration or files are introduced. PHP errors are shared across sites; request history identifies host, HTTP/HTTPS, original path, status and duration without query strings. Framework logs, SQL queries and terminal output are outside this viewer.

Log snapshots read nine fixed files outside the service-manager lock, capped at 64 KiB and 120 entries per file, 4 KiB per displayed message, and 240 rendered matches, prioritizing errors and warnings before recent unclassified/activity output. Only one native read runs at a time; unchanged snapshots avoid rebuilding the view. Legacy binary TLS requests receive a readable protocol-mismatch explanation, and valid UTF-8 URL paths display in Unicode. They preserve multiline traces, wait for complete writes, handle replacement/truncation, and retain reader position while its entry remains in recent history. Polling stops off-page or when the document is hidden. Files over 2 MiB are trimmed to their latest 256 KiB only before the owning service starts; running files may grow until the next start. Linux log commands are unchanged. See [the accepted design and validation scope](docs/log-viewer-consideration.md).
