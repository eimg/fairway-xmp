# Fairway XMP development environment

This specification describes current behavior. Development follows current requirements; successful automated builds are published when the owner authorizes them. See [documentation](docs/README.md).

## Product

Display name: **Fairway XMP** on Windows, macOS and Linux. The green application mark is shared by the app, Windows installer, and uninstaller. The macOS bundle is `/Applications/Fairway XMP.app`; installer hooks and removal target only that bundle.

A classroom PHP development environment with a desktop control panel on Windows/macOS and a terminal dashboard on Linux.
Supported targets: Windows 10 22H2 / Windows 11 x64, macOS 15+ Apple Silicon, and Linux x86_64 with glibc 2.35+. Linux ships as a terminal edition; CI covers its installer and five distro runtimes, with release-owner testing still encouraged.
No Docker/WSL requirement, distro-specific Linux packages, ARM Linux or musl support, Intel Mac packages, Laravel-specific project management, or a preinstalled Node/npm requirement for the PHP services/desktop app. All platforms bundle the unchanged fnm CLI; the macOS and Windows apps offer optional Node downloads.

## Application and runtimes

Tauri 2, Rust service manager, React/TypeScript UI. Exact versions and required PHP extensions are recorded in `runtime-manifest.json`. Download inputs are pinned by SHA256 in `runtime-downloads.lock.json` once prepared and reviewed. Runtime preparation never installs Homebrew or system services.

The runtime includes PHP CLI/FastCGI, Nginx, MySQL, phpMyAdmin, Composer, Mailpit, CA trust roots, native runtime libraries and upstream notices. Exact versions and extension requirements belong in `runtime-manifest.json`. Mac Nginx is compiled from its pinned upstream source using pinned PCRE2/OpenSSL bottles and the macOS SDK's zlib. No system installation or Homebrew service is required. Windows inputs are official x64 ZIP distributions with checked SHA256 pins.

Current builds bundle PHP 8.2–8.5, with PHP 8.5 selected by default. PHP 8.0 and 8.1 are not included. A saved `php-version` of 8.0 or 8.1 is left on disk and blocks service startup until the user chooses PHP 8.2 or later. The desktop remains open with Settings available; Linux accepts `fairway php-version 8.2` (or another bundled branch). Failed recovery saves restore the old selection, generated configuration and launchers; live service PID markers also block recovery switching. One persisted `php-version` selection controls websites, CLI PHP, and Composer. Desktop selection is a dropdown inside collapsed Advanced settings, saved with the ports; Linux exposes `fairway php-version`. Switching requires stopped services, validates the selected runtime, and regenerates configurations and installed CLI launchers. Failed settings changes restore the previous configuration. Windows loads the ZIP extension DLL only when present; Linux recovery verifies the selected PHP-FPM executable.

Desktop Settings includes a separate curated PHP settings card for memory limit, execution time, upload size, timezone, displayed errors and session upload progress. It initially shows the active branch (8.5 by default), with other branches in a collapsed version selector. Editing an inactive branch never switches PHP or changes active generated files. Active saves require stopped Nginx/PHP; MySQL and Mail may continue running. Settings apply to generated configuration used by web PHP, CLI and Composer, with CLI PHP's normal execution-time exception. Values are validated, including timezones from the selected bundled interpreter. Only deviations from current defaults are stored in `php-settings.json` under application data, keyed by minor PHP version, so patch/runtime/app updates retain choices while unmodified fields follow current defaults. Reset removes that branch's overrides. Failed saves restore the previous override file and generated configurations. Upload size controls `upload_max_filesize`; `post_max_size` and Nginx `client_max_body_size` add 8 MiB for form overhead. Nginx `fastcgi_read_timeout` follows the selected PHP execution limit plus 30 seconds; PHP unlimited mode uses a 24-hour Nginx response-idle timeout, not a zero/immediate timeout. This HTTP-level directive is inherited by localhost, phpMyAdmin and registered HTTP/HTTPS sites. PHP execution and response-idle time remain distinct. Session upload progress stays enabled by default and can be disabled without disabling normal file uploads. Raw INI and extension editing are outside this UI. See [PHP settings](docs/php-settings.md).

Generated PHP configuration uses the standard development `variables_order=GPCS`. Host variables remain available through `getenv()` and `$_SERVER`, while application code such as Dotenv populates `$_ENV`. Laravel's development-server environment filtering therefore preserves Fairway's `PHPRC`, `PHP_INI_SCAN_DIR` and `MIBS` settings when launching child PHP processes and restarting after `.env` changes.

Linux uses a separate `cli` Cargo feature, without Tauri, WebView or GUI dependencies. Runtime inputs are SHA256-pinned in `runtime-linux-downloads.lock.json`; PHP and Nginx are compiled on the glibc 2.35 baseline. MySQL uses the official generic x86_64 archive. Each component bundles its native library closure with relative RUNPATHs; MySQL and PHP OpenSSL versions remain isolated. Build validation rejects newer glibc symbol requirements. Corresponding source archives include the exact app commit, PHP/Nginx/MySQL sources and Ubuntu sources/patches for copied libraries.

Source builds require `pdo_pgsql` and `pgsql` in every bundled PHP version for applications using a user-supplied PostgreSQL server. Windows enables the shipped DLLs in generated PHP configuration; Mac uses the existing compiled client extensions. Linux builds both extensions against libpq and bundles its dependency closure and corresponding sources using the glibc 2.35 baseline. Linux build reuse checks the PHP version and all required extensions so pre-client builds are rebuilt. Runtime verification checks the required extensions in all PHP versions. PHP runtime packaging includes client support only. PostgreSQL server packaging, administration utilities, service lifecycle, a desktop Data browser adapter and environment backup/update integration remain future work. Runtime verification does not prohibit adding PostgreSQL components later. Existing MySQL/SQLite behavior remains. Candidate workflows exercise both APIs through generated configuration in CLI and Nginx/PHP requests against isolated external SCRAM-authenticated test servers. See `docs/postgres-client-support.md`.

Every bundled PHP version also requires `sockets`, `soap` and `ldap` on all three platforms. Windows enables the existing DLLs; macOS uses its compiled extensions; Linux builds them with LDAP client libraries and bundles their native library closure, notices and corresponding sources. `platformExtensions` additionally requires `pcntl` and `posix` on macOS/Linux for CLI workers; Windows has no native PCNTL/POSIX support. Linux build reuse validates these platform-specific requirements too. Installer workflows check socket I/O, SOAP dispatch, LDAP initialization/options/escaping in CLI/web and signal/child-process behavior in Unix CLI, without shipping external servers. LDAP smoke checks do not authenticate against a real directory. Redis uses project-installed Predis with a user-supplied server; native Redis/AMQP extensions are not included. See [PHP clients and worker support](docs/php-client-support.md).

## Linux terminal edition

`fairway` opens the ANSI terminal dashboard; CLI commands provide status (including JSON), Start/Stop/Restart all or Nginx/MySQL/Mail, logs, ports, backup, bundled PHP/Composer/MySQL tools, a shell and managed PATH integration. PHP-FPM follows Nginx; PHP CLI does not require starting web services. phpMyAdmin uses the displayed browser URL.

The Linux package includes upstream fnm unchanged in runtime/fnm/bin and exposes bare `fnm` through CLI integration and `fairway shell`. No `fairway fnm`/`fairway node` wrapper, Node auto-install or shell activation is added on Linux. Existing Node on the invoking shell’s PATH takes precedence. Linux source packages include fnm’s complete corresponding sources. Installation/removal overlap guards protect fnm stores, and uninstall preserves installed Node versions.

A detached user supervisor owns the service manager. A private Unix socket and lifetime advisory lock coordinate multiple clients; mutations run sequentially, while status/log requests report busy promptly during an operation. Requests identify the installation before performing actions. The services and supervisor do not run as root; local `.test` address setup uses a short-lived privileged helper after the user approves it. No systemd dependency or automatic service startup. `q`/Ctrl+C close the TUI while services persist; `Q`/`fairway shutdown` queue graceful shutdown after pending operations, then stop services and the supervisor. TUI commands are delivered before acknowledging their keys, so closing immediately cannot cancel an accepted action. Failed shutdown leaves the controller available. Linux process recovery verifies `/proc` executable and exact service configuration before adopting MySQL/Nginx/PHP-FPM; recovered ownership also checks process start time to reject a reused PID.

The offline `.run` and equivalent `.tar.gz` install under `~/.local/share/fairway-xmp` (custom dedicated prefix optional), with versioned release directories and a current symlink. Reinstallation backs up initialized student databases and gracefully shuts down before switching runtimes. Bash/Zsh integration exposes Fairway/PHP/Composer; other shells can invoke the absolute path. Uninstall always preserves coursework, databases and backups. Manual updates only; no desktop updater on Linux.

Linux installation prefixes must be separate from the document root and application data, with overlap checks resolving symlink ancestors and parent traversal. Uninstall removes only the managed releases and current link, refuses removal when the payload overlaps protected user storage, and retains any other files within the prefix. An empty prefix is removed; a nonempty prefix retains its installation marker so reinstall can reuse it without accepting arbitrary existing directories. Failed service/domain/trust/CLI cleanup leaves the installation files in place.

Modal text fields and dropdowns use an inset keyboard focus ring. Sites and database forms share a padded scrolling body with fixed headings and action footers; focused controls, scrollbars, and buttons stay inside the modal at the 820×650 minimum size. Small controls and buttons retain a visible outer focus ring with space around it.

Page headings and sidebar navigation omit decorative eyebrow captions. The desktop sidebar groups Environment, Terminal and Logs at the top, Manage Sites / View Mail / Browse Data under a subtle divider, and Settings / Updates in a group anchored above Getting started and a centered version at the bottom. Fold, in the workspace breadcrumb, collapses that sidebar to icons and gives the width back to the page; Unfold restores the labels. Very narrow windows stay icon-only without the fold control. Group names are available to assistive technology without visible captions; the local-learning badge and repeated product name are omitted. The XMP brand label uses normal letter spacing.

Operation results appear in a fixed, dismissible notification without scrolling the page or moving focus. This covers environment, settings, updates, and site actions, and the same treatment is used for mail inbox actions, terminal session and folder results, and log copy results. Successes use polite status announcements and errors use assertive alerts; long messages scroll within a bounded notification and remain until dismissed, replaced by another operation, or cleared by navigation. Page-specific results that arrive after navigation are suppressed. Identical backend error events are deduplicated until a different error or a new explicit operation. CLI enable/disable messages retain the new-terminal/restart-editor instruction. Persistent page state stays inline, including missing-runtime warnings, current service status, an unreadable saved site list, inbox load failures, and log-file read failures; long inline text scrolls inside its own block. Dialog validation stays in its dialog and scrolls inside a height-capped message. Logs auto-follow and terminal focus remain independent. Terminal session failures stay with that session across navigation.

Environment places Nginx, PHP, MySQL and phpMyAdmin in a 2×2 grid, with Mail in a compact full-width row below. Mail groups its identity and status on the left, inbox address in the middle, and service/log controls on the right; unavailable/error details use their own row. Narrow layouts stack these groups without removing controls. A separate Workspace details section pairs Document root and Database connection in equal-width reference cards with matching headings and action footers. Document-root paths wrap in full. The redundant Environment terminal shortcut is removed; Terminal remains available in the sidebar and through Ctrl+backtick.

Data browser navigation preserves its workspace state across sidebar visits. Database/table loading replaces catalog metadata and rows together, keeps the previous view visible and inert until ready, and uses one delayed local indicator without dimming controls or shifting layout. If an individual table or view cannot load, the new catalog and selection remain available with empty row/structure data, an inline error and retry; the SQL editor and other tables remain usable. Old rows are never shown under the failing selection. The native operation guard remains active. Returning during cancellation waits for the prior request before refreshing.

## Services

Default loopback ports: website 8800, phpMyAdmin 8801, MySQL 13306, internal PHP FastCGI 19000, mail inbox 8802, mail SMTP 11025. Settings saved before the mail catcher keep all existing ports. On first load, missing mail ports use the defaults or the next distinct unprivileged port when a default is already configured for another service; the chosen ports are saved atomically. Explicitly saved mail ports are never reassigned, and invalid settings are preserved and reported.

Mail runs Mailpit's official release binary as an optional fifth service, bound to 127.0.0.1 with its database under application data. Start all includes it when the runtime has it; a runtime without it keeps every other service usable. PHP's `mail()` uses it through `sendmail_path` (`mailpit sendmail`) on macOS/Linux and `SMTP`/`smtp_port` on Windows, so mail never leaves the computer. Mailpit writes no PID file, so Fairway records `mail.pid` and, on macOS/Linux, adopts a leftover Mailpit only when its executable and exact command line match. The desktop Mail page is a native inbox: the backend reads Mailpit's REST API over loopback (list/search, open, delete, delete all, and saving an attachment through a native save dialog) and the page polls while open. Embedded CID raster images load from Mailpit as data URLs (up to 16 images, 2 MiB each and 4 MiB total); missing or oversized parts keep the message readable and report incomplete images. HTML email renders in an opaque sandboxed `srcdoc` frame without same-origin access. Email scripts and metadata are removed in an inert template; the frame's restrictive CSP authorizes only Fairway's hash-pinned link/keyboard bridge, keeping email scripts, forms and browser remote-resource requests blocked. Remote `<img>` elements load automatically when a message is opened, using a separate native loader for at most 16 images per message, 2 MiB each, sequentially. There is no image-loading checkbox or hide action. Loading placeholders have no action; download or decode failures offer Retry image with the error in its tooltip. Only trusted retry clicks from the current opaque frame can retry a failed image, and the parent maps its ID to the prepared message URL. HTML/Text switches preserve downloaded images and failures without refetching; opening another message discards the previous queue and pending results. It accepts credential-free HTTP/HTTPS URLs and passive raster MIME types, validates at most three redirects without HTTPS downgrade, checks response size while streaming, and uses three-second connect and ten-second per-request timeouts. Cookies, authorization, referrers, proxies, automatic retries and decompression are disabled; TLS verification stays enabled. Results are data URLs, so app and preview image policies remain self/data and data-only respectively. CSS images, SVG, fonts, frames and scripts remain blocked. The loader intentionally supports local development addresses for outgoing-mail debugging; image hosts can learn the reader's IP and opening activity. Placeholders offer retry on download or decode failure. Parent messages must come from that exact frame; user-activated HTTP/HTTPS links (including linked buttons) open in the default browser through a native command that validates the destination; the preview never navigates. Other URL schemes and relative links stay blocked. It also offers the SMTP address and Laravel `.env` settings; The Mail card on Environment opens this page, which uses the full window width; Mailpit's own web UI remains available through Open in browser. Opening, deleting, and saving attachments report success and failure in the fixed notice. Inbox polling failures stay in the message list.
Nginx owns two listeners and serves phpMyAdmin; phpMyAdmin is not an independent server process.

Sites are explicit registrations saved in `sites.json` in the data directory: a display name, a DNS-label domain served as `<domain>.test`, an absolute web root anywhere on disk, an HTTPS flag, and an optional "route missing paths to index.php" fallback. Nothing is discovered from folders and there is no framework detection. An existing `projects.json` is read once, written as `sites.json`, and removed. Registering, editing, or removing a site validates the list, writes the Nginx configuration, and runs `nginx -t` and reload; on failure the previous list and configuration are restored, so the basic localhost server keeps working. A missing web root is shown as unavailable; its server stays configured and answers 404, so restoring the folder restores service without another edit. After a change, Fairway syncs only its marked hosts-file block to the registered domains with OS administrator approval; a declined or failed sync leaves the site saved and the UI offers a retry. Startup and service controls never initiate address permissions or certificate trust changes. A previously requested macOS helper approval is recorded durably: the native monitor finishes that pending address update after approval, including after restart, without reopening Settings or taking focus. It reads the latest registered domains under the normal operation guard. Sites shows Waiting for macOS approval with separate Check approval and Open System Settings actions while waiting; unrelated controls stay usable. An explicit check refreshes the helper registration and applies the current domains if macOS reports it enabled, without reopening Settings or unregistering the job. Pending checks show neutral, actionable feedback, which clears on later completion. Successful completion clears the pending marker; a genuine write failure clears automatic continuation and leaves an explicit retry. Hosts mismatches without a pending approval request are not repaired automatically. Removing a site keeps its files. Uninstall removes the managed entries. Port 80 and portless site addresses are not part of this release.

Desktop Sites uses responsive entries with full URLs, web root paths, readiness states, Copy URL, and a compact actions menu with left-aligned single-line labels, icons, and a divider before Remove site for opening the web root, opening a site terminal, editing, and removing. A page-level web-server control starts Nginx/PHP without starting MySQL; unavailable/runtime/address/HTTPS/server states explain why Open is disabled. Save messages use the returned readiness and HTTP/HTTPS URL. An unreadable saved list surfaces an error with retry and the saved-list path, disables registration changes, and is never shown as an empty list; CLI status and the TUI also report the error. The add/edit form uses an explicit App type choice for direct file serving or a front controller, readable helper text, and a conditional warning when the chosen root is inside the shared document root. All sites use the displayed shared PHP version.

Each site can enable HTTPS on loopback port 8443 without changing HTTP on port 8800; Linux exposes `fairway site https DOMAIN on|off`. Fairway creates one local `.test`-constrained certificate authority and signs a leaf certificate containing the exact HTTPS domains. The first enable installs per-user trust (macOS login keychain, Windows user Root store, Linux system store via sudo/pkexec) after an explanation; private keys stay in the user's application data. Removing the last HTTPS site also removes the trust. In the desktop app, disabling HTTPS on the last enabled site removes unused trust in the same operation, after applying the site/config change. Cancelled or failed cleanup leaves HTTPS off, reports the partial result and retains the explicit certificate-removal retry; other enabled HTTPS sites retain shared trust; uninstall also removes it and clears saved HTTPS flags. Laravel applications can set `APP_URL` to the secure URL for generated links.

Unknown HTTP hosts are rejected by explicit default servers on the website/phpMyAdmin ports, while localhost, 127.0.0.1, configured ports and registered site routes remain available. HTTPS rejects unknown SNI and unknown Host names. New local CAs encode `.test` DNS restrictions, all-IP exclusions, TLS-server purpose and zero subordinate depth. The elevated Linux helper validates the actual bounded certificate bytes and policy; exact fingerprinted anchors and root-owned temporary copies prevent filename/path substitution. Existing roots migrate through staged material and approval before a generation-pointer publication; site configuration/reload precedes old-root retirement, and cancellation leaves enabled sites and retry markers intact. Sites exposes Update certificate trust only when needed. Cached leaf signatures, keys and SANs are checked before reuse. The main renderer has event-only core permissions; production CSP denies objects, base overrides and browser form navigation while retaining sandboxed mail and native open/dialog workflows. Verifier-specific trust-anchor limits and testing are documented in `docs/security-boundaries.md`.

Start all preflights all ports before launching. Ports are validated, distinct, unprivileged, and saved only while services are stopped. Conflicts suggest an available alternative and show the occupying application where available. No silent port reassignment.

On macOS, preflight and alternative-port checks supplement the bind probe with a bounded IPv4 loopback connection check to detect existing wildcard/dual-stack listeners. IPv6-only listeners remain compatible with Fairway's IPv4 services, and normal port-reuse behavior is preserved.

The application tracks processes it starts. Nginx startup starts PHP; stopping or restarting Nginx through the panel or tray also stops or restarts its PHP worker. PHP has status and logs in the panel but no independent service controls in the panel or tray. PHP CLI remains available without running web services. Internally, stopping PHP first stops Nginx. Starting/stopping MySQL is independent. A partial Start all failure rolls back newly started services while retaining previously running ones. MySQL is shut down through authenticated mysqladmin and is never forcibly killed; an owned instance without a completed-provisioning marker may fall back to explicitly passwordless mysqladmin for recovery from older interrupted first-run setup. Provisioned instances never use that fallback. A surviving MySQL instance can be recovered only when its PID and exact runtime/config command identity match this installation. On macOS and Linux, startup also recovers surviving Nginx and the selected PHP-FPM master only when both their executable path and exact service/configuration title match. A crash or force quit therefore leaves services controllable after reopening; unrelated processes and other Fairway data directories are not adopted.

Minimizing and closing the window leave the application and services running. On macOS, closing the window hides the Dock icon and leaves the menu bar available; showing the window restores the Dock icon. Minimizing keeps the Dock icon. A native macOS menu bar / Windows system tray menu offers Show Fairway XMP, Start all, Stop all, individual Nginx/MySQL/Mail Start/Stop, Open phpMyAdmin, and Quit. On macOS and Windows, small colored bitmap dots occupy the native menu icon column. macOS uses non-template images to preserve status colors and explicitly requests image visibility through `NSMenuItem.preferredImageVisibility` when the setter is available (macOS 27+); older versions retain standard menu image behavior. Windows bitmap dots avoid monochrome emoji rendering. Each platform controls native icon spacing and text layout. Nginx/MySQL/Mail show green when ready and red when stopped or not ready. Start all and Stop all use plain text without dots. Their enabled state reflects the owned processes (PHP, Nginx, MySQL, and Mail when available); phpMyAdmin is not counted as another process. Stop all remains enabled when only Mail runs, and Start all remains enabled when Mail is available but stopped. Runtimes without Mail can reach the fully started state, while a running Mail process is always counted even if its binary was removed. The status snapshot reports actual Mailpit executable availability as `mailAvailable`. The macOS tray Quit item displays the native Cmd+Q shortcut. phpMyAdmin shares Nginx and has no independent Start/Stop. Reopening the app restores the existing window; macOS Dock reopening does the same.

Tray and panel actions share one Rust operation guard and service manager. Native status monitoring continues while the window is hidden. Quit (including macOS Cmd+Q/application Quit) prevents new operations, waits for an existing operation, and gracefully stops all services before allowing exit. Repeated quit requests cannot bypass shutdown. If shutdown fails, the window reopens with the reason and an explicit choice: Keep open to retry, or Quit anyway to leave remaining services running and close embedded terminals. MySQL is never force-killed. On Windows, named per-installation/service jobs let remaining web services survive this explicit exit and be recovered through retained process handles and verified job membership on reopening. An explicitly retained service holds one job handle until exit so the job name survives the original controller closing; reopening does not duplicate that retained handle again. It excludes filesystem paths, logs, service error text, credentials, and project/database contents. Local source edits are marked in build identity and rejected by clean-candidate recording. Current verification guidance is in `docs/testing.md`.

Normal UI review can use `npm run dev:ui`: the same React screens with an explicitly labeled, development-only simulated backend. A toolbar selects stopped/running/partial/conflict/missing-runtime/update and CLI detection/disabled scenarios, with example Windows/macOS paths. Paths default to the browser host platform; Windows launchers use backslashes and `.cmd`, while macOS uses Unix paths. Installed commands remain distinct from missing or other inherited commands in CLI fixtures. Service actions, settings, logs, backups, and update responses are in-memory simulations with visible pending states; native open actions only show a message. Reset/reload clears the simulation. Ordinary browser previews remain disabled and production builds cannot activate this mode.

Playwright runs Chromium and WebKit at 1080×760 and 820×650, checks UI interactions and overflow, and attaches scenario screenshots to an HTML report. Failures retain traces, videos, and screenshots. The `ui-review` CI job uploads the report for human visual review during explicitly dispatched verification and release-candidate runs. Ordinary pushes and pull requests do not start application verification or the full browser suite. A new manual verification cancels an older verification on the same ref. Screenshots are review evidence, without approved pixel-diff baselines. Browser review and native service CI must use the same source commit; they do not replace targeted native checks of installers, tray menus, OS integration, native WebView differences, or the Linux terminal dashboard.

Desktop CI compiles applications, dependencies, helpers and lifecycle probes without signing secrets, then transfers unsigned inputs to fresh packaging runners. Signing runners use the locked Tauri CLI with npm lifecycle scripts disabled and no restored build caches; source commits must already be in fetched main history and match the build exactly. Standalone comparison refs are validated before their checkout. Apple credentials are removed immediately after signing/notarization, before executing bundled PHP/app checks; updater keys are supplied only to direct version-bound signing commands. Existing installer/updater lifecycle checks remain required. Repository write permission is limited to publication jobs, which use a signature verifier compiled in a separate read-only job. See [signing/build separation](docs/build-and-release.md#signing).

Installer workflows reuse checksum-verified upstream download caches and Rust release dependency caches. A separate manual-only warmer prepares these on request, either directly or through the verification workflow's `warm_inputs` checkbox; it never signs or publishes a candidate. Linux staged runtime and corresponding-source caching uses the same composite preparation action in warm-up and installer builds, with verification on every restore. Source collection and lifecycle probe compilation precede desktop distribution signing/packaging. Existing installer compression and all candidate release checks remain required. See docs/ci-build-performance.md.

Core tests cover port validation/conflicts, path quoting, and idempotent PATH-block removal. Packaging tests reject archive traversal and bad checksums. The runtime smoke example verifies actual browser → Nginx → PHP → MySQL → response, phpMyAdmin rendering, database backup, graceful shutdown, settings persistence, and removal of isolated CLI integration without deleting coursework. The native SQLite smoke checks every bundled PHP version with Unicode home/data paths, backups, destructive guards and cancellation. Windows database workers load their selected PDO driver with an isolated startup configuration relative to the PHP runtime, avoiding php.ini startup paths that require NTFS short-name aliases.

Candidate source collection preserves the committed source lock. Ordinary archives require their pinned SHA256. Gitiles snapshots with a pinned revision and full Git tree may change archive compression only when every file, symlink and executable mode still reproduces that exact tree; the shipped inventory records the actual archive SHA256. Tests cover recompression and reject changed content, modes, revisions, and tree pins.

Linux CI exercises offline installation, concurrent first clients, real terminal rendering and detach, PHP/Composer, HTTP/PDO queries, backup, crash recovery, safe port changes, reinstall and uninstall with isolated paths containing spaces, apostrophes and non-ASCII characters. Clean distro containers verify bundled runtimes on Ubuntu 22.04/24.04, Debian, Fedora and Arch without installing runtime dependencies. Docker is used only for CI verification.

## Development and release policy

Current product requirements drive development. New behavior should preserve existing coursework, credentials and saved choices, and keep this specification synchronized. Open opportunities and practical limitations are in [Maintenance](docs/maintenance.md).

Builds and publication are separate. Successful automated candidates report `ready-for-publication`; the owner can authorize publishing them without device acceptance JSON or manual checklist completion. `publish-release.yml` publishes the exact successful candidate after checking version/source/tag identity, artifact hashes and update signatures. Changes to application/runtime inputs require a new automated build. Device testing is optional and reported only when performed. The publisher never claims unperformed manual tests passed.

Stable and preview version ordering controls update delivery, not development scope. Feed promotion is explicit and off by default. Existing preview/stable feed URLs remain valid for installed clients; database upgrade fixtures and prior-installer lifecycle baselines remain compatibility tests. See [Build and release](docs/build-and-release.md).

## Troubleshooting logs

The desktop has one global Logs page in the core group below Terminal. Service log buttons open this viewer with the corresponding source selected; there are no separate log dialogs. The tagline is Recent output from all sites and services. Live/Paused appears in the title row using the same status badge and dot as Terminal and Mail, and remains in the compact maximized header. Site, source and Search share one toolbar row with an entry count and a Log options menu. Problems only defaults on; its checked toggle, Live/Pause, paused Refresh, Clear view and Copy shown are grouped in that menu. There is no bottom hint block; the output uses the recovered vertical space. Shared PHP scope stays explicit when filtering by site. Clear hides the current bounded snapshot and service-status rows only in this view, across all filters, so unchanged rows stay hidden on subsequent polls; service-message IDs include backend occurrence generations, so an identical error from a new retry reappears even if no intermediate recovery was observed while the view was paused, off-page or hidden; cleared occurrences stay hidden in the retained paused snapshot; new rows or changed text under an existing ID remain visible. Clearing preserves filters and Live/Paused state, stays in effect across navigation, and resets on app reload. It never truncates, deletes or rewrites log files. Open log folder sits in the title row and uses the existing native logs-folder action. A failed copy uses the fixed notice; snapshot and file-read failures stay with the log list. Warnings, failed requests and unclassified output remain visible by default. The Site filter uses recorded request host metadata: an address scope shows its requests plus PHP output explicitly labeled Shared PHP / All sites. Other service logs and older requests without a recorded host stay in All sites. Registered and recently observed hosts are offered, and service shortcuts clear site scope. No new per-site logging configuration or files are introduced. PHP errors are shared across sites; request history identifies host, HTTP/HTTPS, original path, status and duration without query strings. Framework logs, SQL queries and terminal output are outside this viewer.

Log snapshots read nine fixed files outside the service-manager lock, capped at 64 KiB and 120 entries per file, 4 KiB per displayed message, and 240 rendered matches, prioritizing errors and warnings before recent unclassified/activity output. Only one native read runs at a time; unchanged snapshots avoid rebuilding the view. Legacy binary TLS requests receive a readable protocol-mismatch explanation, and valid UTF-8 URL paths display in Unicode. They preserve multiline traces, wait for complete writes, handle replacement/truncation, and retain reader position while its entry remains in recent history. Polling stops off-page or when the document is hidden. Files over 2 MiB are trimmed to their latest 256 KiB only before the owning service starts; running files may grow until the next start. Linux log commands are unchanged. See [testing guidance](docs/testing.md).
